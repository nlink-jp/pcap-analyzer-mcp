# 実地ノート — 実マルウェアを含むキャプチャを解析するとき

> Date: 2026-07-26

`samples/` の合成キャプチャでは再現しない、**実際の悪性キャプチャでだけ起きること**を
記録する。

実測の出典: Unit 42「Wireshark を使った pcap からのオブジェクト抽出」の演習用 pcap
5 本を v0.1.0 で解析（2026-07-26）。HTTP / SMB / IMF / FTP-DATA の 4 プロトコルを通した。

## 1. アンチウイルスが `extract_objects` を EPERM で落とす

### 症状

本物のマルウェアを含む pcap に `extract_objects` をかけると、抽出そのものは成功して
いるのに次のエラーで失敗する。

```json
{
  "code": "analysis_failed",
  "message": "open /.../work/out/objects/_raw/Invoice&MSO-Request.doc: operation not permitted"
}
```

`operation not permitted` は EPERM である。本サーバーの権限設定やパス検証の問題では
なく、**ホストの AV が書き込み途中のファイルを掴んで隔離した**結果である。失敗後は
`_raw` がロールバックされるため、後から中身を調べる材料も残らない。

実測環境: macOS (Darwin 25.5) + Intego VirusBarrier のリアルタイム保護、tshark 4.0.17。

**1 個でも隔離されると呼び出し全体が失敗する。** 演習 pcap の 1 本目では 3 オブジェクト
中 2 個（`Invoice&MSO-Request.doc` と `knr.exe`）が検知され、良性の `ncsi.txt` を含めて
1 件も返らなかった。部分成功はしない。

### なぜ起きるか

ADR-0007 の脅威 2 が予測したとおりである。`--export-objects` が吐くのは「マルウェア
かもしれないファイル」であり、それをユーザーの Mac に書き込む以上、AV が反応するのは
**誤作動ではなく正常動作**である。実際にマルウェアなのだから、これは誤検知ではなく
**正しい検知**である。

### defang が対策できること・できないこと

defang（`<sha256>.bin` / 0600 / 実行ビットなし）が下げるのは次の 2 つであり、
**AV の検知はそこに含まれない**。

| defang が対策すること | 手段 |
|---|---|
| **事故による実行** | 実行ビットを立てず 0600 で保存する |
| **ファイル名そのものが攻撃である場合** | 回線由来の名前をパスに使わない。tshark が実際に書いた `object1.text%2fplain` は、デコードされてパスに到達すればディレクトリトラバーサルになる |

AV は**ファイル名や拡張子ではなく中身のシグネチャ**を見るため、`<sha256>.bin` に
リネームしても検知は起きる。そして**それを防ぐことは目標ではない** — 正しい検知を
抑止すれば、それは検知回避（evasion）だからである。「defang は AV 対策ではない」とは
そういう意味であり、defang の設計が不足しているという意味ではない。

### 切り分け

| 観察 | 意味 |
|---|---|
| 良性オブジェクトだけのキャプチャでは同じ操作が全件成功する | ツール・podman・パス設定は正常。切り分け対象から外せる |
| 実行ファイルや文書を含むキャプチャでだけ EPERM | **検体が本物である**ことのシグナルとして使える |
| エラー中のファイル名が AV の通知・隔離ログのファイル名と一致する | 確定。推測で切り分ける必要はない |

`container_failed`（podman が動いていない）や `path_not_allowed` とは別物である。
エラーコードは `analysis_failed`、メッセージは必ず `_raw/` 配下のファイルを指す。

### 対処 — ワークスペースの AV 除外と、それが持ち込む危険

現実的な回避策は、**ワークスペースディレクトリを AV の除外設定に加える**ことである。
ただしこれは**保護を意図的に外す操作**であり、代償を理解した上で選ぶこと。

⚠️ 除外を設定した瞬間に起きること:

- そのディレクトリに書かれた**生きたマルウェアが隔離されないまま残る**
- 以後そこに置かれるものすべてが AV の保護外になる。解析と無関係なファイルも含む
- defang は効いたままだが、それが守るのは**事故実行とファイル名由来の攻撃**だけで、
  検体そのものは無害化されない。AV という層が外れた分、防御は素で薄くなる

守るべき運用:

- 除外は**解析専用の使い捨てディレクトリ 1 つ**に限る。ホームディレクトリやプロジェクト
  ルートごと除外しない
- 解析が終わったら**抽出物を削除し、除外設定も元に戻す**
- 除外したまま放置しない。恒久設定にしたくなったら、それは次項の専用環境へ移すべき兆候

### 推奨: 解析はホストで行わない

本筋は、**AV の入っていない使い捨て環境**（専用 VM / CI コンテナ）で解析パイプラインを
回すことである。

- AV との衝突が起きない
- 生きた検体がユーザーの日常環境に残らない
- 除外設定という恒久的な穴を開けずに済む

ホストの Mac で回すのは、対話的な調査を手早く済ませたい場合に限る。その場合も上の運用を
守ること。

## 2. `ftp-data` はバイナリ RETR を書き出さない

### 症状

FTP でマルウェアが 5 本ダウンロードされているキャプチャに
`extract_objects(protocol: "ftp-data")` をかけても、`.exe` は **1 件も返らない**。
同じキャプチャの ASCII モード `STOR`（窃取ログの HTML）だけが取れる。

### 確認したこと

tshark 4.0.17 の ftp-data ディセクタの制約である。以下を切り分け済み:

- **AV の隔離ではない** — 上記の除外を設定したパスで再実行しても結果は変わらない（1 件のまま）
- **本サーバーの問題でもない** — Wireshark GUI でも同じで、Unit 42 の記事自身が
  「`.exe` は Follow TCP Stream → Save as Raw で取れ」と書いている

### 回避

バイト列が要らないなら、**メタデータだけで大半の調査は完結する**。

```
query_packets(filter: "ftp.request.command or ftp.response.code",
              fields: ["ftp.request.command", "ftp.request.arg",
                       "ftp.response.code", "ftp.response.arg"])
```

ファイル名・転送方向（`RETR` / `STOR`）・サイズ（`SIZE` に対する `213` 応答）・認証情報
（`USER` / `PASS` は平文）がすべて取れる。実測では 5 本の `.exe` の名前とバイトサイズが
完全に揃った。

バイト列が要る場合は `list_conversations` でデータコネクションのストリーム番号を取り、
`follow_stream` でレンジ読みする。
