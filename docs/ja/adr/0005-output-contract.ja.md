# ADR-0005: 出力契約 — バイト閾値・JSONL・形状不変

- Status: Accepted
- Date: 2026-07-26
- Driver: magi
- Revisions: 2026-07-26 — Track E で `delivery` フィールドを追加
- Generalises to: 組織 ADR 候補（`.github/adr/`）— 大きい結果を返す MCP ツール全般に適用できる

---

## Context

本プロジェクトの成否を決めるのは、実のところ tshark の使いこなしではなく **結果をどう返すか**である。`tshark -V` は 1 パケットで数百行、`-T json` は 1000 パケットで数 MB になる。MCP ツールの戻り値はすべてエージェントのコンテキストに載るため、素直に返せばコンテキストが焼き切れて解析が続行不能になる。

移植元 data-toolbox-mcp は `query_data` に行数上限（既定 20000 行）を設け、v0.4.0 で `truncated` / `total` を追加した。この経験から得られている知見は 2 つある。

- 上限に達したことを黙って切り捨てると、LLM は「これが全件だ」と誤解する。`truncated` と `total` の開示が必要
- 生成物を返す経路（v0.2.1 の `host_work_dir` 追加、v0.3.0 の `attach_files`）は後付けになり、UX 不具合として実機検証で露見した

pcap 固有の事情として、**行数では出力サイズを制御できない**という問題がある。`ip.src,ip.dst` だけを抽出した 10000 行より、ペイロード列を含む 100 行のほうが大きいことがざらにある。

## Decision

結果を返すすべてのツールが、以下の統一契約に従う。

### 1. 閾値はシリアライズ後のバイト数

インライン返却するかファイルに落とすかは、**JSON にシリアライズした後のバイト数**で判定する（`[output] inline_max_bytes`、既定 65536）。行数（`default_row_limit`、既定 10000）は副次的なガードとして併用するが、主たる制御はバイト数とする。

### 2. インラインでもファイルでも形状を変えない

```json
{
  "workspace_id": "...",
  "filter": "tcp.flags.reset == 1",
  "matched": 48213,
  "returned": 200,
  "truncated": true,
  "delivery": "file",
  "rows": [ "... インライン時のみ ..." ],
  "result_file": "<workspace>/work/out/q3.jsonl",
  "result_bytes": 48231904,
  "sample": [ "... ファイル出力時のみ、先頭数行 ..." ]
}
```

エージェントに分岐を書かせないため、共通フィールドは常に同じ位置・同じ意味を持つ。

**`delivery`（`"inline"` / `"file"`）は Track E の実装中に追加した。** 当初は「`rows` があればインライン、`result_file` があればファイル」とキーの有無で判別する設計だったが、実装してみると **0 件のインライン結果で `rows` が空配列になり、`omitempty` で消えてファイル出力と区別が付かなくなる**ことが判明した。`rows` をポインタにして空配列を保持したうえで、判別を推測に頼らせないよう明示フィールドを設けた。

### 3. `matched` を常に返す

`matched` は **display filter に合致したパケットの総数**であり、`returned`（実際に返した行数）とは独立に必ず返す。これが無いとエージェントは「絞り込みが効いたのか、そもそも該当が無いのか」を判別できず、次の一手を誤る。

実装上は tshark の 2 パスが必要になる場合がある。common path のコストを避けるため、**`truncated` になったときのみ件数取得のための追加パスを行う**（data-toolbox v0.4.0 の `total` と同じ考え方）。追加パスがタイムアウトした場合は `matched_unavailable_reason` を返す。

### 4. ファイル出力時も `sample` を添える

先頭数行（既定 5 行）を必ずインラインに含める。これが無いと、エージェントは「中身の形を知るためだけの往復」を強いられる。

### 5. 大きい出力は JSONL、単一 JSON 配列にしない

- `head` / `grep` / `tail` で部分的に読める
- DuckDB が `read_json_auto` でそのまま読む
- ストリーミング書き出しができるため、サーバー側でも全件をメモリに載せずに済む

CSV も選択できる（`format` 引数）。parquet は ADR-0003 の帰結として提供しない。

### 6. 出力ファイルは「全部読むもの」ではない

出力ファイルは **(a) 次のツール（data-toolbox-mcp / DuckDB）への入力**、または **(b) 部分読み・grep** の対象として設計する。エージェントが全体を読むことは想定しない。この前提は `get_usage` で明示する。

### 7. 時刻は epoch と UTC ISO-8601 の両方

ローカルタイムゾーンで整形した時刻は返さない。タイムゾーンの取り違えは IR の分析で致命的な誤りにつながる。

## Consequences

**Positive:**

- コンテキストを焼き切る事故が構造的に防止される。エージェントは常に「絞り込みが足りない」ことを `matched` と `truncated` から知り、フィルタを強める方向に自己修正できる
- インライン / ファイルで形状が同じなので、エージェント側のツール利用コードが単純になる
- JSONL により、巨大な結果でもサーバー・エージェント双方がストリーミング的に扱える
- `sample` により、ファイル出力時の往復が 1 回減る

**Negative:**

- **`matched` の取得に追加の tshark パスが必要になる場合がある。** truncate 時に限定してもなお、巨大な pcap では無視できないコストになりうる。タイムアウトと `matched_unavailable_reason` によるフォールバックが必要
- シリアライズ後のバイト数で判定するため、**一度シリアライズしてからファイル出力に切り替える**実装になりうる。行を積みながら逐次バイト数を数え、閾値を超えた時点でファイルへ切り替える実装にして、二度手間を避ける必要がある
- 出力ファイルが `work/out/` に蓄積し続ける。`delete_workspace` 以外の自動 GC は v1 では提供しない（`describe_workspace` の `outputs[]` で可視化するに留める）
